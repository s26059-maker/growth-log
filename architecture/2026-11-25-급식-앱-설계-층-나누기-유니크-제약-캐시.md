# 급식 앱 설계: 층 나누기, 유니크 제약, 캐시

> 📅 2026-11-25 · 아키텍처 · 85점
> `#아키텍처` `#레이어드` `#유니크제약` `#캐시` `#Redis`
> 800명이 쓰는 급식 앱을 Controller-Service-Repository로 나누고, 중복 별점은 DB 유니크 제약으로, 몰리는 메뉴 조회는 Redis 캐시로 해결

## 요구사항

- 학생 **800명**이 쓰는 "오늘의 급식" 앱
- 아침 7~8시랑 점심 직전에 몰림 (1분에 수백 명이 메뉴를 봄)
- 급식 메뉴는 영양사 선생님이 **하루 한 번** 등록
- 학생은 메뉴에 **별점(1~5점)**을 남길 수 있음. 한 메뉴에 **한 사람당 한 번만**

## 층 나누기

요청이 들어오면 세 층을 차례로 거쳐. 이걸 **레이어드 아키텍처**라고 해. 식당으로 치면 주문 받는 직원, 요리사, 창고 관리인이 각자 자기 일만 하는 거야.

| 층 | 하는 일 | 별점 남기기에서 |
|---|---|---|
| Controller | 요청 받고 응답하기 | 점수가 1~5인지 입력 검사 |
| Service | 비즈니스 규칙 처리 | 이미 남겼는지 확인 → 저장 지시 |
| Repository | DB 읽고 쓰기 | 별점 저장, 중복 조회 |

## 별점 중복 막기

서비스에서 "이미 남겼어?"를 확인하는 것만으로는 부족해. 버튼을 **동시에 두 번** 누르면 두 요청이 둘 다 "없음"을 보고 둘 다 저장해버려 (**경쟁 상태**).

그래서 DB에 **유니크 제약**을 걸어. "같은 학생 + 같은 메뉴 조합은 딱 한 줄만"이라는 규칙이야.

```sql
ALTER TABLE rating ADD CONSTRAINT uk_student_menu UNIQUE (student_id, menu_id);
```

`rating` 테이블

| id | student_id | menu_id | score |
|---|---|---|---|
| 1 | 101 | 7 | 5 |

101번 학생이 7번 메뉴에 한 번 더 저장하려고 하면

| 결과 |
|---|
| ❌ `Duplicate entry '101-7'` 에러, 저장 안 됨 |

**서버가 2대여도 막히는 이유**: 서버(접수 창구)는 2개여도 DB(명부)는 1권이야.

| 순서 | 서버 A | 서버 B | DB |
|---|---|---|---|
| 1 | "이미 남겼어?" → 없음 | "이미 남겼어?" → 없음 | (101, 7) 없음 |
| 2 | 저장 요청 | | ✅ 저장됨 |
| 3 | | 저장 요청 | ❌ 이미 있음 → 거절 |
| 4 | "완료" 응답 | 에러 잡아서 "이미 남겼어" 응답 | 딱 1줄 |

**중요한 점**: 자바 락은 **각 서버 안에서만** 통해서 서버가 늘어나면 소용없어. DB 제약은 **모든 서버가 같이 쓰는 곳**에 있어서 서버가 몇 대든 통해.

```java
@Transactional
public void rate(Long studentId, Long menuId, int score) {
    if (ratingRepository.existsByStudentIdAndMenuId(studentId, menuId)) {
        throw new IllegalStateException("이미 별점을 남겼어요");
    }
    try {
        ratingRepository.saveAndFlush(new Rating(studentId, menuId, score));
    } catch (DataIntegrityViolationException e) { // 동시에 눌러서 DB가 거절한 경우
        throw new IllegalStateException("이미 별점을 남겼어요");
    }
}
```

## 메뉴 보기는 캐시로

자주 보는 걸 빠른 곳에 **미리 올려두는 것**을 **캐시**라고 해. 메뉴는 하루 한 번 바뀌는데 800명이 반복해서 봐서 캐시에 딱이야.

```
학생 → Controller → Service → Redis에 오늘 메뉴 있어?
   ├ 있으면 → 바로 응답 (DB 안 감)
   └ 없으면 → DB 조회 → Redis에 올려둠 (유효기간: 하루) → 응답
영양사가 메뉴 등록/수정 → 그 날짜 캐시 삭제
```

```java
@Cacheable(value = "menu", key = "#date")      // 캐시에 있으면 메서드 실행 안 하고 바로 반환
public MenuResponse getMenu(LocalDate date) { ... }

@CacheEvict(value = "menu", key = "#date")     // 메뉴가 바뀌면 그 날짜 캐시 삭제
public void registerMenu(LocalDate date, MenuRequest request) { ... }
```

## 이렇게 한 이유

- **층 나누기**: 역할이 안 섞여서 고치기 쉽고 테스트도 쉬움
- **규칙은 서비스**: "한 번만" 같은 비즈니스 규칙을 한 곳에 모아둠
- **DB 제약은 마지막 방어선**: 서버를 늘려도 중복이 절대 안 생김
- **메뉴는 캐시**: 읽기는 엄청 많고 쓰기는 거의 없는 데이터라 캐시 효과가 큼

## 내가 놓쳤던 점

- 처음엔 층별 역할을 일반적으로만 말함. 기능 하나(별점)를 기준으로 **구체적으로** 나눠야 설계
- 자바 **락**은 서버가 여러 대면 못 막음 → DB **유니크 제약**이 확실함
- 메뉴 조회에 **카프카**를 쓴다고 함. 카프카는 메시지를 전달하는 우체국이고, 조회를 빠르게 하는 건 **캐시(Redis)**
