# 스레드가 많으면 빨라질까

> 📅 2026-11-24 · CS · 80점
> `#운영체제` `#컨텍스트스위칭` `#스레드풀` `#커넥션풀`
> 스레드를 늘려도 코어 수가 한계인 이유와 메모리·컨텍스트 스위칭 비용, DB 커넥션 풀 병목까지 정리

## 코어 수가 한계

CPU 코어는 실제로 일하는 **손**이야. 코어가 8개면 진짜로 동시에 도는 스레드는 **8개뿐**이야.
나머지는 OS가 아주 빠르게 **번갈아** 돌려서 동시에 도는 것처럼 보이는 거야.

그래서 톰캣 스레드를 200개에서 2000개로 늘려도 10배 빨라지지 않아.

**중요한 점**: 한계는 스레드 수가 아니라 **코어 수**야.

## 스레드가 많으면 생기는 비용

- **메모리**: 스레드마다 자기 **스택**을 따로 가져 (보통 1MB). 2000개면 스택만 2GB야
- **컨텍스트 스위칭**: 책상 하나를 여러 명이 번갈아 쓰는 거랑 같아. 사람이 바뀔 때마다 앞 사람 짐을 치우고 내 짐을 펼쳐야 하지
  - CPU도 스레드를 바꿀 때마다 **"어디까지 했는지"**(다음에 실행할 위치, 계산하던 값)를 저장하고 다음 스레드 걸 불러와
  - CPU 캐시에 있던 데이터도 다시 채워야 해
  - 스레드가 너무 많으면 **일하는 시간보다 바꾸는 시간**이 더 많아져

## 늘리면 도움 되는 경우

스레드가 DB나 외부 API 응답을 **기다리면서 노는 시간**이 길면, 그동안 다른 스레드가 CPU를 쓸 수 있어.
이럴 땐 스레드를 어느 정도 늘리면 이득이야.

**중요한 점**: 적정 개수는 감으로 정하지 않고 **부하 테스트로 재서** 정해.

## 실무에서는

```yaml
server:
  tomcat:
    threads:
      max: 200                # 동시에 요청을 처리할 스레드 최대 개수 (기본값)
spring:
  datasource:
    hikari:
      maximum-pool-size: 10   # DB 커넥션 최대 개수 (기본값)
```

스레드가 2000개여도 DB 커넥션이 10개면 1990개는 DB 앞에서 줄 서서 기다려.
이러면 진짜 병목은 스레드가 아니라 **DB**야. 스레드 수를 늘리기 전에 커넥션 풀이랑 느린 쿼리부터 봐야 해.

## 내가 놓쳤던 점

- 스레드가 많아질 때 문제는 힙이 줄어드는 게 아니라, **스택이 스레드마다 늘어나서** 메모리를 먹는 것
- 컨텍스트 스위칭은 "어디까지 했는지"를 **저장하고 불러오는** 비용
- I/O 대기가 길면 스레드를 늘리는 게 **도움이 될 수도** 있음
