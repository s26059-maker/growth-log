# 프로세스와 스레드, 그리고 경쟁 상태

> 📅 2026-11-23 · CS · 60점
> `#운영체제` `#스레드` `#경쟁상태` `#스레드풀`
> 톰캣이 요청마다 스레드를 쓰는 이유를 메모리 구조로 이해하고, 경쟁 상태와 막는 법을 정리

## 프로세스와 스레드

프로세스는 **실행 중인 프로그램**이고, 스레드는 그 프로세스 **안에서 일하는 실행 흐름**이야.
집으로 비유하면 프로세스는 **집 한 채**, 스레드는 **그 집에 사는 가족**.

## 메모리 구조

프로그램 메모리는 4칸으로 나뉘어.

| 칸 | 들어가는 것 | 스레드끼리 |
|---|---|---|
| 코드 | 실행할 코드 | 공유 |
| 데이터 | 전역 변수, static | 공유 |
| 힙 | `new`로 만든 객체 | 공유 |
| 스택 | 함수 호출, 지역 변수 | **각자 따로** |

- 힙 = **거실** (다 같이 씀)
- 스택 = **각자 방** (내 지역 변수는 나만 봄)

프로세스는 이 4칸을 **통째로 따로** 받아. 스레드는 스택만 새로 받고 나머지는 같이 써.

## 왜 요청마다 스레드를 쓸까

- **만들기가 싸다**: 새 프로세스는 메모리를 전부 새로 잡아야 해 (집 새로 짓기). 스레드는 스택만 있으면 돼 (식구 한 명 늘리기)
- **바꾸기가 싸다**: CPU가 하던 일을 바꾸는 걸 컨텍스트 스위칭이라고 해. 스레드끼리는 메모리가 같아서 전환이 가벼워
- **공유가 쉽다**: 같은 힙을 쓰니까 데이터를 주고받을 때 따로 통로가 필요 없어

**중요한 점**: 그래서 톰캣은 요청 하나를 스레드 하나로 처리해.

## 경쟁 상태

공유하는 거실(힙)에 여러 스레드가 **동시에** 쓰면 값이 꼬여. 이걸 **경쟁 상태(race condition)**라고 해.

```java
@Service
public class VisitService {

    private int count = 0; // 싱글톤 빈의 필드 = 힙 = 모든 요청 스레드가 공유

    public void visit() {
        count++; // 읽기 → +1 → 쓰기, 세 단계라 중간에 다른 스레드가 끼어들 수 있음
    }
}
```

두 스레드가 동시에 `count`를 0으로 읽고 각자 1을 쓰면, 2번 방문했는데 **1**만 남아.

## 막는 방법

- **한 번에 한 명만**: `synchronized`나 `Lock`으로 감싸서 한 스레드만 들어가게 (화장실 문 잠그기)
- **애초에 공유 안 하기**: 상태를 필드에 두지 말고 **지역 변수**로 (각자 방인 스택에 있으니 안전)
- 숫자 하나 세는 정도면 `AtomicInteger`도 있어

**중요한 점**: Spring 빈은 기본이 싱글톤이라 **필드에 상태를 두면 위험**해. 서비스는 상태 없이 만드는 게 기본이야.

## 스레드 풀

스레드도 매번 만들고 버리면 비용이 쌓여. 그래서 톰캣은 **스레드 풀**에 스레드를 미리 만들어두고 재사용해 (기본 최대 200개).
다 바쁘면 남은 요청은 **대기 큐**에서 줄 서서 기다려.

- 캐시: **데이터**를 저장해두고 재사용
- 스레드 풀: **일꾼(스레드)**을 미리 뽑아두고 재사용

## 내가 놓쳤던 점

- 스레드마다 따로 있는 칸은 힙이 아니라 **스택**. 힙은 공유라서 경쟁 상태가 생기는 곳
- 스레드를 미리 만들어두는 건 캐시가 아니라 **스레드 풀**
- 경쟁 상태를 **막는 방법**(synchronized, 상태 없는 빈)까지 말해야 답이 완성됨
