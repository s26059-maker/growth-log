# 데드락은 왜 생기고 어떻게 막을까

> 📅 2026-11-25 · CS · 75점
> `#운영체제` `#데드락` `#락` `#트랜잭션`
> 두 스레드가 락을 반대 순서로 잡을 때 생기는 데드락과 락 순서 통일, 타임아웃으로 막는 법, MySQL 데드락까지 정리

## 데드락

두 스레드가 **서로 상대가 쥔 걸 기다리면서 영원히 멈추는** 상태야. 우리말로 **교착 상태**.
좁은 골목에서 차 두 대가 마주 보고, 서로 상대가 먼저 비켜주길 기다리는 상황이야.

## 어떻게 생기나

- 주문 스레드 A: `재고` 잠금 → `포인트` 잠금
- 환불 스레드 B: `포인트` 잠금 → `재고` 잠금

둘이 동시에 돌면 이렇게 돼.

| 순서 | 스레드 A | 스레드 B |
|---|---|---|
| 1 | 재고 잠금 ✅ | 포인트 잠금 ✅ |
| 2 | 포인트 기다림 ⏳ (B가 쥠) | 재고 기다림 ⏳ (A가 쥠) |
| 3 | 영원히 대기 | 영원히 대기 |

## 경쟁 상태와 차이

| | 경쟁 상태 | 데드락 |
|---|---|---|
| 무슨 일 | 동시에 들어가서 **값이 꼬임** | 서로 기다리다 **아무도 못 나감** |
| 원인 | 락이 **없어서** | 락을 **잘못 써서** |

## 막는 방법

**락 순서 통일** (제일 흔한 방법): 둘 다 `재고 → 포인트` 순서로 잡아.

| 순서 | 스레드 A | 스레드 B |
|---|---|---|
| 1 | 재고 잠금 ✅ | 재고 기다림 ⏳ (아무것도 안 쥠) |
| 2 | 포인트 잠금 ✅ → 처리 → 둘 다 놓음 | |
| 3 | | 재고 잠금 ✅ → 포인트 잠금 ✅ → 처리 |

B가 **아무것도 안 쥔 채로** 기다리니까 서로 엉키는 원이 안 생겨.

**기다리다 포기**: 정해진 시간 안에 못 잡으면 쥔 것도 놓고 나중에 다시 시도해.

```java
if (stockLock.tryLock(1, TimeUnit.SECONDS)) {
    try {
        if (pointLock.tryLock(1, TimeUnit.SECONDS)) {
            try {
                // 재고, 포인트 처리
            } finally {
                pointLock.unlock();
            }
        }
    } finally {
        stockLock.unlock();
    }
}
// 못 잡았으면 쥔 걸 다 놓은 상태라 나중에 다시 시도하면 됨
```

**한 번에 다 잡기 / 락 하나로 합치기**: 확실하지만, 재고만 필요한 작업도 포인트까지 잠가버려서 동시에 할 수 있는 일이 줄고 **느려져**.

**중요한 점**: "상대가 쥐었는지 먼저 확인하고 잡기"는 위험해. 확인하는 순간과 잡는 순간 사이에 상대가 끼어들 수 있거든. 그래서 확인과 잡기를 한 번에 하는 `tryLock`을 써.

## 실무에서는

MySQL에서도 트랜잭션 두 개가 행을 **반대 순서로** 수정하면 데드락이 나.
MySQL(InnoDB)은 이걸 감지해서 한쪽 트랜잭션을 강제로 **롤백**시켜.

그래서 실무에서는
- 여러 행을 수정할 땐 **수정 순서를 통일**하고
- 데드락으로 실패하면 **다시 시도**하는 코드를 넣어

## 내가 놓쳤던 점

- 처음에 **경쟁 상태**라고 답함. 값이 꼬이는 게 아니라 **멈추는 거라서** 데드락
- "상대를 보고 잡기"는 확인과 잡기 사이에 끼어들 수 있어서 위험함. 시간 제한 있는 `tryLock`으로
- 제일 흔한 해결책인 **락 순서 통일**을 못 떠올림
