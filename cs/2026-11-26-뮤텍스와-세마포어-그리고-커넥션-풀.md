# 뮤텍스와 세마포어, 그리고 커넥션 풀

> 📅 2026-11-26 · CS · 80점
> `#운영체제` `#뮤텍스` `#세마포어` `#커넥션풀`
> 열쇠 1개(뮤텍스)와 숫자판(세마포어)의 차이를 화장실 비유로 이해하고, DB 커넥션 풀이 세마포어처럼 동작하는 원리를 정리

## 뮤텍스

**화장실 1칸, 열쇠 1개**야.

- 들어가는 사람이 열쇠를 가져가고, 나올 때 돌려놔
- 열쇠가 없으면 밖에서 기다려
- 한 번에 **딱 1명**. 그리고 잠근 사람만 열 수 있어

임계 구역에 한 스레드만 들어가게 하는 **상호 배제**가 이거야. 자바에서는 `synchronized`나 `Lock`.

## 세마포어

**화장실 3칸, 입구에 "남은 칸: 3" 숫자판**이야.

- 들어갈 때 숫자 **-1**, 나올 때 **+1**
- 숫자가 **0**이면 밖에서 기다려
- 한 번에 **N명까지** 동시에 들어갈 수 있어

```java
Semaphore semaphore = new Semaphore(3); // 칸 3개
semaphore.acquire();  // 들어가기 (-1), 0이면 기다림
// 화장실 사용
semaphore.release();  // 나오기 (+1)
```

**중요한 점**: 세마포어는 열쇠를 하나하나 관리하는 게 아니라 **"남은 자리 수" 숫자 하나**로 관리해.

| | 뮤텍스 | 세마포어 |
|---|---|---|
| 동시에 몇 명 | 1명 | N명 |
| 관리 방법 | 열쇠 1개 | 숫자(남은 자리 수) |
| 비유 | 화장실 1칸 | 화장실 3칸 + 숫자판 |

## 실무에서는: DB 커넥션 풀

커넥션 10개는 **열쇠 10개**라서 **세마포어**랑 비슷하게 동작해.

- 10개가 다 쓰이고 있으면 **11번째 요청은 기다려**
- 누가 커넥션을 반납하면 그걸 받아가
- HikariCP는 기본으로 **30초**까지 기다리고, 그래도 못 받으면 **에러**를 내

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 10      # 커넥션 개수 = 세마포어 숫자
      connection-timeout: 30000  # 커넥션을 기다리는 최대 시간 (ms, 기본값)
```

**중요한 점**: 느린 쿼리 하나가 커넥션을 오래 쥐고 있으면 뒤에 줄이 계속 길어져. 그래서 DB 성능 튜닝이 서버 전체 속도를 좌우해.

## 내가 놓쳤던 점

- 처음엔 뮤텍스와 세마포어 차이를 몰라서 밑바닥부터 다시 배움
- 커넥션을 무한정 기다리는 게 아니라 **30초** 안에 못 받으면 **에러**
- 세마포어는 열쇠 여러 개가 아니라 **숫자 하나**(남은 자리 수)로 관리
