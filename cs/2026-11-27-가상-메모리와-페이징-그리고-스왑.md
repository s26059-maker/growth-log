# 가상 메모리와 페이징, 그리고 스왑

> 📅 2026-11-27 · CS · 75점
> `#운영체제` `#가상메모리` `#페이징` `#스왑`
> 램보다 많은 메모리를 쓰는 프로그램들이 같이 돌아가는 이유를 가상 메모리와 페이지 폴트로 설명하고, 서버의 스왑과 JVM 힙 설정까지 연결

## 가상 메모리

램이 8GB인 노트북에서 크롬, 인텔리제이, 게임을 같이 켜면 메모리 합이 8GB를 넘어도 꺼지지 않고 돌아가. **가상 메모리** 덕분이야.

운영체제는 프로그램마다 실제 램보다 큰 "자기만의 메모리 공간"을 줘. 프로그램은 큰 메모리를 혼자 쓰는 줄 알지만, 실제로는 운영체제가 그중 **지금 쓰는 부분만** 램에 올려둬.

램을 **책상**, 디스크를 **책장**이라고 생각하면 쉬워. 책상이 좁아도 지금 보는 책만 펴두고 안 보는 책은 책장에 꽂아두면, 책을 아주 많이 다룰 수 있어.

## 페이징과 스왑

- 메모리는 **페이지**라는 작은 조각(보통 4KB)으로 나눠서 관리해
- 당장 안 쓰는 페이지는 디스크의 **스왑 영역**으로 내보내 (윈도우에서는 페이지 파일)
- 프로그램이 디스크로 내려간 페이지를 찾으면 **페이지 폴트**가 나. 운영체제가 그 페이지를 디스크에서 램으로 다시 읽어오고, 램에 자리가 없으면 다른 페이지를 내보내

## 왜 느려질까

디스크는 램보다 훨씬 느려. SSD도 램보다 수백 배 넘게 느리고, 하드 디스크는 수만 배 느려. 책상에서 책을 집는 것과 창고에 다녀오는 것 차이야.

그래서 페이지 폴트가 잦으면 렉이 걸려. 이게 너무 심해져서 일보다 페이지 옮기는 데 시간을 더 쓰는 상태를 **스래싱**이라고 해. 책상이 너무 좁아서 책 읽는 시간보다 책장을 왔다 갔다 하는 시간이 더 긴 거지.

## 실무에서는

서버도 똑같아. 메모리가 모자라서 스왑이 일어나면 API 응답이 갑자기 느려져.

그래서 JVM 힙 크기(`-Xmx`)는 서버 램보다 넉넉히 작게 잡아. 힙 말고도 스레드마다 필요한 스택, 운영체제가 쓸 메모리가 따로 있어야 하거든.

```bash
# 램 4GB 서버라면 힙은 절반 정도로 여유 있게
java -Xms2g -Xmx2g -jar app.jar
```

**중요한 점**: 힙을 램만큼 꽉 채워 잡으면, 오히려 스왑이 나서 서버 전체가 느려질 수 있어.

## 내가 놓쳤던 점

- 처음엔 CPU **스케줄링**과 섞어서 설명함. 스케줄링은 CPU를 쓰는 순서를 정하는 거고, 이건 메모리 얘기
- 안 쓰는 페이지가 가는 곳을 **롬**이라고 함. ROM은 읽기만 되는 메모리라 못 쓰고, 정답은 **디스크(스왑 영역)**
- 가상 메모리, 페이지 폴트라는 이름과 디스크가 **얼마나** 느린지를 빠뜨림
